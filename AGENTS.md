# Working on Hutch

My instructions for any coding agent working in this repo.

This repo is the project's only memory. When a conversation produces a decision, a changed plan or a new finding, write it into the docs in the same PR; anything left only in a chat is lost.

## What to read

| When | Read |
|------|------|
| Every session | `docs/plan.md` (what's next) and `docs/decisions.md` (what's settled, what's open) |
| Before proposing product changes | `docs/context.md`: research, and why some obvious features are deliberately absent |
| Any UI, visual or web work | `design/README.md`, then `design/brand.md` |

## The work loop

1. **Find the work.** Open the milestone named under **Now** in `docs/plan.md`. If I asked for something else, do that instead.
2. **Check it's unblocked.** If it depends on a decision marked **Proposed** or **Open**, stop and ask. Record the answer in `docs/decisions.md`.
3. **Confirm the slice.** Restate the milestone's "Done when" in one or two lines and say what you'll do this session. One milestone, or one clear slice of one, per session.
4. **Build on a branch,** with tests.
5. **Prove it.** Green build and tests (see Building the iOS app), plus a simulator screenshot for UI work.
6. **Close the loop in the same PR:** tick the milestone in `docs/plan.md`, move **Now** to the next one, and record any new decision or finding.
7. **Report briefly:** what changed, how to check it, what's next.

## Talking to me

I often check in from my phone while work runs on my Mac. Keep replies short and lead with the outcome; I can't comfortably read long diffs on a small screen.

## Non-negotiables

1. **Zero-knowledge.** Plaintext item data, photos, names and keys never leave the device. The server stores and returns opaque ciphertext only. Every sync feature needs a test that asserts the server payload is not readable.
2. **Private by default.** New items are `private`. Nothing becomes lendable or for-sale without an explicit user action.
3. **No hand-rolled crypto.** Use CryptoKit on iOS (WebCrypto if the web ever handles data); no custom ciphers or homemade key schedules. Explain any crypto choice in the PR.
4. **Recovery before sync.** Never ship a way to lose the only key without a recovery path.
5. **No third-party analytics or trackers.**

## Repo layout

- `apps/ios` — SwiftUI iPhone app. Project generated by XcodeGen from `project.yml`; never hand-edit `.xcodeproj`. Core logic (models, crypto, sync) in a local Swift package with tests.
- `apps/web` — static site for myhutch.app (landing, App Store link, privacy policy, support). Plain HTML/CSS or a minimal static generator; no tracking.
- `design/` — the design system both apps follow: `tokens.json` (colors, type, spacing; the single source of truth), `brand.md` (logo), `explorations/` (rejected rounds). Never hard-code a color or size in an app that should come from tokens.
- `docs/` — plan, decisions, context.

## Building the iOS app

Work happens on my Mac, in `~/Projects/hutch`, where Xcode is installed. Build and test locally:
- Regenerate the project after changing `project.yml`: `xcodegen generate` in `apps/ios`.
- Build and run tests against an iPhone simulator with `xcodebuild test` (pick an installed simulator with `xcrun simctl list devices available`).
- Never call work done without a green local build and test run, and say which simulator it ran on.
- For UI changes, launch the app in the simulator and take a screenshot (`xcrun simctl io booted screenshot`) so I can see the result on my phone.
- Keep logic in the Swift package so it's covered by unit tests.
- CI on a GitHub macOS runner is an optional safety net, not the main loop: macOS minutes are expensive. If added, scope it to `apps/ios/**` and pull requests only.

**If the session is not on the Mac** (a cloud session with no link to the laptop), it cannot build Swift. Say so, limit the work to docs or the website, or ask me to open the session from my Mac.

## Design: iPhone first

- Design for iPhone screens first; support every current iPhone size, Dynamic Type and dark mode from the start.
- Standard SwiftUI components and system behavior over custom chrome; one-handed reach for primary actions (add item, scan).
- iPad and the website are secondary.

## Conventions

- Swift: Swift 6, strict concurrency, Swift Testing. Web: no framework unless needed.
- Tests alongside code.
- Small PRs. Commit messages say *why*, not just what.
- Secrets (Cloudflare tokens, eBay keys) live in GitHub/Cloudflare secrets, never in the repo.
